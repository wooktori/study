## 1. 동적 모듈 로딩이 사용되는 구체적인 사례

### 정적 import vs 동적 import

```js
// 정적 import — 파일 최상단에서 항상 로드
import { Chart } from "./chart.js";

// 동적 import — 필요한 시점에 로드
const { Chart } = await import("./chart.js");
```

동적 `import()`는 Promise를 반환하고, 런타임에 필요할 때 모듈을 로드한다.

### 사례 1 — 코드 스플리팅 (라우팅)

SPA(Single Page Application)에서 현재 페이지에 필요한 코드만 로드한다.

```js
// React Router 방식
const routes = [
  {
    path: "/dashboard",
    component: () => import("./pages/Dashboard.js"), // 해당 페이지 진입 시에만 로드
  },
  {
    path: "/settings",
    component: () => import("./pages/Settings.js"),
  },
];

// 초기 번들: 라우터 코드만 포함
// /dashboard 진입 시: Dashboard.js 추가 로드
```

### 사례 2 — 조건부 로딩

특정 조건에서만 필요한 모듈을 로드한다.

```js
// 관리자만 사용하는 기능
async function loadAdminPanel(user) {
  if (!user.isAdmin) return;
  const { AdminPanel } = await import("./AdminPanel.js");
  new AdminPanel().render();
}

// 브라우저 환경에서만 필요한 모듈
if (typeof window !== "undefined") {
  const { initAnalytics } = await import("./analytics.js");
  initAnalytics();
}
```

### 사례 3 — 무거운 라이브러리 지연 로딩

초기 로딩 속도를 높이기 위해 무거운 라이브러리를 나중에 로드한다.

```js
// 버튼 클릭 시에만 차트 라이브러리 로드 (수백 KB)
button.addEventListener("click", async () => {
  const { default: Chart } = await import("chart.js");
  new Chart(canvas, config);
});

// PDF 생성 버튼 클릭 시
exportBtn.addEventListener("click", async () => {
  const { generatePDF } = await import("./pdf-generator.js");
  generatePDF(data);
});
```

### 사례 4 — 언어/테마 등 설정 기반 로딩

```js
// 사용자 언어에 맞는 번역 파일만 로드
async function loadLocale(lang) {
  const messages = await import(`./locales/${lang}.js`);
  return messages.default;
}

loadLocale("ko"); // ./locales/ko.js 만 로드
loadLocale("en"); // ./locales/en.js 만 로드
```

### 정적 import와 동적 import 비교

| 구분        | 정적 import        | 동적 import() |
| ----------- | ------------------ | ------------- |
| 위치        | 파일 최상단만 가능 | 어디서든 가능 |
| 실행 시점   | 파일 로드 시 즉시  | 호출 시점     |
| 반환        | 없음 (선언)        | Promise       |
| 조건부 사용 | ❌                 | ✅            |
| 트리 쉐이킹 | ✅                 | 제한적        |

> **정리:** 동적 import는 초기 로딩 성능 향상, 조건부 로딩, 코드 스플리팅이 필요한 상황에서 사용한다. 무조건 필요한 모듈은 정적 import를, 선택적으로 필요한 모듈은 동적 import를 사용한다.

## 2. ESM이 정적 모듈 시스템으로 설계된 이유

### 정적이란?

import/export가 **런타임이 아닌 파싱 단계에서** 결정된다는 의미다.

```js
// ✅ ESM — 정적: 항상 최상단, 조건 불가
import { add } from "./math.js";

// ❌ ESM에서 불가
if (condition) {
  import { add } from "./math.js"; // SyntaxError
}
const moduleName = "./math.js";
import { add } from moduleName;    // SyntaxError (변수 불가)
```

```js
// CommonJS(CJS) — 동적: 런타임에 결정 가능
if (condition) {
  const { add } = require("./math.js"); // 가능
}
const mod = require(getModuleName()); // 가능
```

### 정적 설계의 이유

**1. 트리 쉐이킹 (Tree Shaking)**

사용하지 않는 코드를 번들에서 제거할 수 있다.

```js
// math.js
export const add = (a, b) => a + b;
export const subtract = (a, b) => a - b; // 사용 안 함
export const multiply = (a, b) => a * b; // 사용 안 함

// main.js
import { add } from "./math.js"; // add만 사용
```

```
정적 분석 결과:
  add      → 사용됨 → 번들에 포함
  subtract → 미사용 → 번들에서 제거 (트리 쉐이킹)
  multiply → 미사용 → 번들에서 제거 (트리 쉐이킹)
```

CJS는 런타임에 결정되므로 빌드 타임에 어떤 코드가 쓰이는지 알 수 없어 트리 쉐이킹이 불가능하다.

**2. 순환 의존성 감지**

```
파싱 단계에서 의존 그래프를 완성
→ A → B → A 순환 감지
→ 실행 전에 경고 가능
```

**3. 병렬 로딩**

모든 의존성을 파싱 단계에서 파악하기 때문에 여러 모듈을 동시에 병렬로 다운로드할 수 있다.

```
CJS: require()를 만날 때마다 순차적으로 로드
ESM: 파싱 후 전체 의존 그래프 파악 → 한 번에 병렬 로드
```

**4. 정적 분석 도구 지원**

```
import { foo } from "./bar.js"
→ 빌드 도구, IDE가 foo가 bar.js에서 왔음을 알 수 있음
→ 자동완성, 타입 추론, 미사용 변수 감지 가능
```

### ESM vs CJS 비교

| 구분               | ESM                   | CommonJS                     |
| ------------------ | --------------------- | ---------------------------- |
| 문법               | `import` / `export`   | `require` / `module.exports` |
| 분석 시점          | 파싱 (정적)           | 런타임 (동적)                |
| 트리 쉐이킹        | ✅                    | ❌                           |
| 병렬 로딩          | ✅                    | ❌                           |
| 조건부 import      | ❌ (동적 import 사용) | ✅                           |
| 브라우저 기본 지원 | ✅                    | ❌                           |

> **정리:** ESM의 정적 설계는 트리 쉐이킹, 병렬 로딩, 정적 분석을 가능하게 한다. 이 세 가지 모두 성능과 개발 경험에 직접적인 영향을 주기 때문에 의도적인 설계 선택이다.

## 3. 모듈에서 실시간 바인딩이란 무엇인지

### 정의

ESM의 `export`는 값을 복사해서 내보내는 게 아니라 **변수에 대한 참조(바인딩)를 내보낸다**. 원본 변수가 바뀌면 import한 쪽에서도 바뀐 값이 보인다.

### CJS vs ESM 비교

```js
// counter.js (CJS)
let count = 0;
module.exports = { count, increment: () => count++ };
```

```js
// main.js (CJS)
const { count, increment } = require("./counter.js");
console.log(count); // 0
increment();
console.log(count); // 0 — ❌ 복사된 값이라 변경 안 됨
```

```js
// counter.js (ESM)
export let count = 0;
export function increment() {
  count++;
}
```

```js
// main.js (ESM)
import { count, increment } from "./counter.js";
console.log(count); // 0
increment();
console.log(count); // 1 — ✅ 실시간 바인딩으로 변경 반영됨
```

### 내부 동작

CJS는 `require()` 시점에 값을 **복사**해 가져온다.

```
CJS: count ──복사──▶ { count: 0 }  (이후 원본이 바뀌어도 복사본은 유지)
ESM: count ──참조──▶ counter.count (항상 원본을 바라봄)
```

### import한 값은 읽기 전용

실시간 바인딩이지만 **import한 쪽에서 직접 수정은 불가**하다.

```js
import { count, increment } from "./counter.js";

count++; // ❌ TypeError: Assignment to constant variable
increment(); // ✅ 모듈 내부에서 수정 → count 반영됨
```

### 활용 사례 — 전역 상태 공유

```js
// store.js
export let isLoggedIn = false;
export function login() {
  isLoggedIn = true;
}
export function logout() {
  isLoggedIn = false;
}
```

```js
// header.js
import { isLoggedIn } from "./store.js";
// login() 호출 후 isLoggedIn이 true로 자동 반영
```

```js
// auth.js
import { login } from "./store.js";
login(); // store.js의 isLoggedIn이 true로 바뀜
// header.js에서도 즉시 true로 보임
```

> **정리:** 실시간 바인딩은 ESM이 값을 복사하지 않고 원본 변수에 대한 참조를 내보내기 때문에 발생한다. import한 쪽에서는 읽기만 가능하고, 원본 모듈 내부에서 값을 바꿔야 반영된다.

## 4. 순환 참조를 문법적으로 금지하지 않은 이유

### 순환 참조란?

```
A.js → B.js → A.js (서로 참조)
```

```js
// a.js
import { b } from "./b.js";
export const a = "A";

// b.js
import { a } from "./a.js";
export const b = "B";
```

### 왜 문법적으로 금지하지 않았나?

**1. 합법적인 사용 사례가 존재한다**

```js
// node.js (트리 구조)
class Node {
  constructor(value) {
    this.value = value;
    this.children = [];
  }
  addChild(node) {
    this.children.push(node);
  }
}

// tree.js
import { Node } from "./node.js";
export class Tree {
  constructor() {
    this.root = new Node(null);
  }
}

// node.js가 Tree를 참조하고, Tree가 Node를 참조하는 구조는 자연스러움
```

**2. 컴파일 타임에 완전히 감지하기 어렵다**

모듈 경계가 동적 경로(`import(path)`)를 포함하면 빌드 전에 순환을 100% 감지할 수 없다.

**3. 언어보다 아키텍처 문제**

순환 참조는 **설계 문제**이기 때문에, 언어가 금지하기보다 개발자가 구조를 잘 설계해야 한다는 철학이 있다.

### 순환 참조의 실제 문제

순환 자체가 문제가 아니라 **초기화 순서** 문제가 발생한다.

```js
// a.js
import { b } from "./b.js";
export const a = `A는 ${b}를 알아`;

// b.js
import { a } from "./a.js";
export const b = `B는 ${a}를 알아`;
```

```
실행 순서:
1. a.js 파싱 → b.js가 필요
2. b.js 파싱 → a.js가 필요 (이미 파싱 중)
3. a.js 바인딩 아직 초기화 안 됨 → b.js에서 a = undefined
4. a.js 실행 → b = "B는 undefined를 알아" (이미 평가됨)
→ a = "A는 B는 undefined를 알아를 알아" (꼬인 결과)
```

### 순환 참조를 해결하는 방법

**방법 1 — 공통 모듈로 분리**

```
❌ A ↔ B (순환)
✅ A → C ← B (공통 의존성 분리)
```

```js
// constants.js (공통)
export const BASE_URL = "https://api.example.com";

// a.js
import { BASE_URL } from "./constants.js"; // A → constants

// b.js
import { BASE_URL } from "./constants.js"; // B → constants
```

**방법 2 — 함수로 감싸기 (지연 평가)**

```js
// a.js
import { getB } from "./b.js";
export const a = () => `A는 ${getB()}를 알아`; // 호출 시점에 평가
```

**방법 3 — 의존 방향 단일화**

```
❌ A → B → A
✅ A → B    (A가 B에만 의존, B는 A 참조 제거)
```

### 순환 참조 감지 도구

```
ESLint: import/no-cycle 규칙
Webpack: circular-dependency-plugin
```

> **정리:** 순환 참조를 금지하지 않은 이유는 합법적인 사용 사례가 있고, 아키텍처 문제는 언어가 아닌 개발자가 해결해야 한다는 철학 때문이다. 실제로는 초기화 순서 문제를 일으키므로 공통 모듈 분리나 함수로 감싸는 방식으로 해결한다.
