## 1. 자바스크립트는 왜 싱글 스레드를 선택했는지

### 배경

자바스크립트는 1995년 브라우저에서 **DOM을 조작하기 위해** 설계됐다.

### 멀티 스레드였다면 생기는 문제

```
스레드 A: button.style.color = "red"
스레드 B: button.style.color = "blue"  // 동시에 실행
→ 어떤 색이 최종 결과? → 예측 불가
```

두 스레드가 같은 DOM 요소를 동시에 수정하면 **경쟁 조건(Race Condition)** 이 발생한다. 이를 막으려면 락(Lock)과 동기화가 필요한데, 이는 웹 개발을 훨씬 복잡하게 만든다.

### 싱글 스레드의 장점

| 장점        | 설명                                 |
| ----------- | ------------------------------------ |
| DOM 안전성  | 한 번에 하나만 실행 → 경쟁 조건 없음 |
| 단순한 모델 | 락, 뮤텍스 없이도 안전               |
| 예측 가능성 | 실행 순서가 명확                     |

### 블로킹 문제는 비동기로 해결

싱글 스레드의 단점(오래 걸리는 작업이 블로킹)은 **이벤트 루프 + Web API + 비동기** 구조로 해결했다.

```
JS 스레드: 코드 실행에 집중
Web API:   네트워크, 타이머 등 오래 걸리는 작업 위임
→ 블로킹 없이 비동기 처리 가능
```

> **정리:** 싱글 스레드는 DOM 조작의 안전성을 보장하기 위한 설계 선택이다. 블로킹 문제는 이벤트 루프와 비동기 처리로 보완한다.

## 2. setTimeout의 최소 지연 시간은 왜 4ms인지

### 현상

```js
const start = Date.now();
setTimeout(() => {
  console.log(Date.now() - start); // 0ms 지정해도 실제로는 4ms 이상
}, 0);
```

### HTML 명세에 정해진 이유

HTML 스펙(WHATWG)은 중첩된 `setTimeout` 호출이 5번 이상이면 **최소 4ms를 강제**한다고 명시한다.

```js
// 중첩 깊이 5 이상에서 최소 4ms 적용
setTimeout(() => {
  setTimeout(() => {
    setTimeout(() => {
      setTimeout(() => {
        setTimeout(() => {
          // 여기서부터 최소 4ms 강제
        }, 0);
      }, 0);
    }, 0);
  }, 0);
}, 0);
```

### 왜 4ms인가?

| 이유             | 설명                                              |
| ---------------- | ------------------------------------------------- |
| CPU 과부하 방지  | 0ms 타이머가 무한 루프처럼 동작하면 CPU 100% 점유 |
| 배터리 절약      | 불필요한 폴링 방지                                |
| OS 타이머 정밀도 | 대부분의 OS 타이머가 ~4ms 단위로 동작             |

### 비활성 탭에서는 더 길어진다

백그라운드 탭에서는 브라우저가 **1000ms(1초)** 로 지연을 늘려 성능을 아낀다.

```js
// 탭이 비활성화되면 setTimeout이 1초마다 실행될 수 있음
setInterval(() => console.log("tick"), 100);
// 백그라운드에서는 100ms가 아닌 1000ms마다 실행
```

> **정리:** 4ms 제한은 CPU 과부하 방지와 OS 타이머 정밀도의 현실적 타협이다. 정밀한 타이밍이 필요하면 `requestAnimationFrame`이나 `performance.now()`를 사용한다.

## 3. Promise.any와 Promise.race의 구체적 사례와 빈 배열을 넣으면

### Promise.race — 가장 먼저 완료된 것 (성공/실패 무관)

```js
// 사례: 타임아웃 구현
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error("시간 초과")), ms),
  );
  return Promise.race([promise, timeout]);
}

withTimeout(fetch("/api/data"), 3000)
  .then((res) => res.json())
  .catch((err) => console.error(err)); // 3초 안에 응답 없으면 "시간 초과"
```

```js
// 사례: 가장 빠른 캐시 서버 선택
const servers = ["https://cdn1.example.com", "https://cdn2.example.com"];
const fastest = await Promise.race(servers.map((url) => fetch(url)));
```

### Promise.any — 가장 먼저 성공한 것 (실패는 무시)

```js
// 사례: 여러 소스 중 하나라도 성공하면 됨
const mirrors = [
  fetch("https://mirror1.example.com/file"),
  fetch("https://mirror2.example.com/file"),
  fetch("https://mirror3.example.com/file"),
];

// mirror1, mirror2가 실패해도 mirror3이 성공하면 OK
const response = await Promise.any(mirrors);
```

```js
// 사례: 번역 API 폴백
const translation = await Promise.any([
  translateWithGoogle(text),
  translateWithDeepL(text),
  translateWithPapago(text),
]);
```

### race vs any 차이

| 메서드 | fulfilled                | rejected                    | 빈 배열                    |
| ------ | ------------------------ | --------------------------- | -------------------------- |
| `race` | 가장 먼저 완료된 것 반환 | 가장 먼저 실패한 것 반환    | 영원히 pending             |
| `any`  | 가장 먼저 성공한 것 반환 | 전부 실패 시 AggregateError | AggregateError 즉시 reject |

### 빈 배열을 넣으면

```js
// Promise.all([]) → 즉시 fulfilled, 빈 배열 반환
Promise.all([]).then((v) => console.log(v)); // []

// Promise.race([]) → 영원히 pending (절대 완료 안 됨)
Promise.race([]); // pending 상태로 멈춤

// Promise.any([]) → 즉시 rejected (AggregateError)
Promise.any([]).catch((e) => console.log(e)); // AggregateError: All promises were rejected

// Promise.allSettled([]) → 즉시 fulfilled, 빈 배열 반환
Promise.allSettled([]).then((v) => console.log(v)); // []
```

> **정리:** `race`는 빠른 응답이 필요하거나 타임아웃을 구현할 때, `any`는 여러 소스 중 하나라도 성공하면 될 때 사용한다. 빈 배열에서 `race`만 pending이 되므로 주의가 필요하다.

## 4. throw와 reject의 차이와 선택 기준

### 실질적 차이가 없는 경우

```js
new Promise((resolve, reject) => {
  reject(new Error("실패")); // 방법 1
});

new Promise((resolve, reject) => {
  throw new Error("실패"); // 방법 2 — 동일하게 rejected 상태가 됨
});
```

Promise 생성자 안에서는 `throw`가 자동으로 `reject`로 변환된다. 결과는 같다.

### 그러나 async 함수 밖에서는 다르다

```js
// ❌ async 함수 밖에서 throw
function notAsync() {
  throw new Error("에러"); // Promise가 아닌 일반 에러 → try/catch 필요
}

// ✅ reject는 항상 Promise 체인으로 전달
function withReject() {
  return Promise.reject(new Error("에러")); // .catch()로 처리
}
```

### 선택 기준

**`throw`를 선택하는 경우**

```js
// 1. async/await 환경 — 동기 코드처럼 보여 가독성 좋음
async function loadUser(id) {
  if (!id) throw new Error("id가 없습니다"); // 자연스럽게 catch로 전달
  return await fetchUser(id);
}

// 2. 조건 검사 후 즉시 중단할 때
async function process(data) {
  if (!data.valid) throw new TypeError("유효하지 않은 데이터");
  // ...
}
```

**`reject`를 선택하는 경우**

```js
// 1. Promise 생성자 내부
const p = new Promise((resolve, reject) => {
  setTimeout(() => reject(new Error("타임아웃")), 3000);
  // throw는 setTimeout 콜백 안에서 Promise를 reject하지 못함
});

// 2. 콜백 기반 코드를 Promise로 래핑할 때
function readFile(path) {
  return new Promise((resolve, reject) => {
    fs.readFile(path, (err, data) => {
      if (err)
        reject(err); // 콜백 안에서는 throw 불가
      else resolve(data);
    });
  });
}
```

### 핵심 차이

| 상황                | throw                    | reject                    |
| ------------------- | ------------------------ | ------------------------- |
| Promise 생성자 내부 | 동작함 (자동 변환)       | 동작함                    |
| async 함수 내부     | ✅ 권장                  | 가능                      |
| 콜백 내부           | ❌ Promise 밖으로 나감   | ✅ 사용해야 함            |
| 가독성              | async/await와 자연스러움 | Promise 체인과 자연스러움 |

> **원칙:** `async/await` 환경에서는 `throw`, Promise 생성자 또는 콜백 내부에서는 `reject`를 사용한다.

## 5. Promise를 취소할 수 있는 표준 방법이 없는 이유

### 현상

```js
const p = fetch("/api/data");
p.cancel(); // ❌ 이런 메서드 없음
```

### 취소가 어려운 이유

**1. Promise는 상태 머신이다**

```
pending → fulfilled
pending → rejected
```

한 번 시작된 Promise는 `fulfilled` 또는 `rejected`로만 끝날 수 있다. "취소됨" 이라는 세 번째 상태를 추가하면 기존 모든 코드가 영향을 받는다.

**2. 체인 어디서 취소할지 불명확하다**

```js
const p = fetch(url)
  .then((res) => res.json())
  .then((data) => process(data))
  .then((result) => display(result));

// p를 취소하면 어느 단계까지 취소? → 정의하기 어려움
```

### 현재 해결 방법 — AbortController

`fetch`에 한해 표준 취소 방법이 있다.

```js
const controller = new AbortController();

fetch("/api/data", { signal: controller.signal })
  .then((res) => res.json())
  .catch((err) => {
    if (err.name === "AbortError") {
      console.log("요청 취소됨");
    }
  });

// 요청 취소
controller.abort();
```

### Promise 취소를 직접 구현하는 패턴

```js
function cancellable(promise) {
  let cancelled = false;

  const wrapped = new Promise((resolve, reject) => {
    promise.then(
      (value) => (cancelled ? reject({ cancelled: true }) : resolve(value)),
      (err) => (cancelled ? reject({ cancelled: true }) : reject(err)),
    );
  });

  return {
    promise: wrapped,
    cancel: () => {
      cancelled = true;
    },
  };
}

const { promise, cancel } = cancellable(fetch("/api/data"));
cancel(); // 결과를 무시하도록 처리
```

> **정리:** Promise에 취소 표준이 없는 이유는 상태 모델의 복잡성, 체인 어느 단계를 취소할지 불명확성, 다중 구독자 문제 때문이다. `fetch` 취소는 `AbortController`로 해결한다.

## 6. setTimeout 콜백과 Promise 후속 처리의 차이, 그리고 비동기 성능 최적화

### setTimeout vs Promise 처리 경로

```js
setTimeout(() => console.log("A"), 0); // Macrotask Queue
Promise.resolve().then(() => console.log("B")); // Microtask Queue

// 출력: B → A
```

```
Call Stack 비워짐
       ↓
Microtask Queue 전부 소진 (Promise 콜백)
       ↓
렌더링
       ↓
Macrotask Queue에서 하나 꺼냄 (setTimeout 콜백)
```

| 구분         | Queue     | 우선순위 | 처리 방식          |
| ------------ | --------- | -------- | ------------------ |
| setTimeout   | Macrotask | 낮음     | 한 번에 하나씩     |
| Promise.then | Microtask | 높음     | 전부 소진될 때까지 |

### Microtask가 너무 많으면 렌더링이 막힌다

```js
// ❌ Microtask가 끝없이 쌓이면 화면이 멈춤
function infiniteMicrotask() {
  Promise.resolve().then(infiniteMicrotask); // 렌더링 블로킹
}

// ✅ setTimeout을 섞어 렌더링 기회를 줌
function yieldToRenderer() {
  return new Promise((resolve) => setTimeout(resolve, 0));
}
```

### 여러 비동기 작업의 실행 시간을 줄이는 방법

**문제: 순차 실행은 느리다**

```js
// ❌ 순차 실행 — 총 3초
const a = await fetchA(); // 1초
const b = await fetchB(); // 1초
const c = await fetchC(); // 1초
```

**해결: 병렬 실행**

```js
// ✅ Promise.all — 병렬 실행, 전부 완료까지 기다림 (총 1초)
const [a, b, c] = await Promise.all([fetchA(), fetchB(), fetchC()]);
```

```js
// ✅ 의존 관계가 있는 경우 — 그룹별 병렬화
const [a, b] = await Promise.all([fetchA(), fetchB()]); // 그룹 1: 병렬
const c = await fetchC(a, b); // 그룹 2: a, b 결과 필요
```

**실행 시간 비교**

```
순차:   A(1s) → B(1s) → C(1s) = 3초
병렬:   A, B, C 동시 시작     = 1초 (가장 오래 걸리는 것 기준)
그룹:   [A,B](1s) → C(1s)    = 2초
```

### Promise.all 에러 처리 주의점

```js
// ❌ 하나라도 실패하면 전부 실패
const [a, b, c] = await Promise.all([fetchA(), fetchB(), fetchC()]);
// fetchB가 실패하면 a, c 결과도 버려짐

// ✅ 실패해도 나머지 결과를 받고 싶을 때
const results = await Promise.allSettled([fetchA(), fetchB(), fetchC()]);
results.forEach((result) => {
  if (result.status === "fulfilled") console.log(result.value);
  if (result.status === "rejected") console.error(result.reason);
});
```

> **원칙:** 독립적인 비동기 작업은 `Promise.all`로 병렬화한다. 실패해도 나머지가 필요하면 `Promise.allSettled`를 사용한다. Microtask가 과도하게 쌓이는 경우 `setTimeout`으로 렌더링 기회를 확보한다.
