## 1. 리액트란 무엇인가

### 리액트란?

페이스북(Meta)이 만든 **UI를 구축하기 위한 JavaScript 라이브러리**다. 프레임워크가 아니라 라이브러리이므로, 라우팅이나 상태관리 같은 기능은 별도 라이브러리를 조합해서 사용한다.

### 리액트를 선택하는 이유

- **컴포넌트 기반** — UI를 독립적인 단위로 쪼개 재사용하고 유지보수하기 쉽다
- **가상 DOM** — 실제 DOM 조작을 최소화해 성능을 최적화한다
- **단방향 데이터 흐름** — 데이터 흐름이 예측 가능해 디버깅이 쉽다
- **생태계** — Next.js, React Query, Zustand 등 풍부한 생태계
- **점유율** — 현재 프론트엔드 라이브러리 중 가장 높은 점유율, 채용 시장 수요가 많다

### 리액트의 주요 기능

| 기능 | 설명 |
|---|---|
| 컴포넌트 | UI를 재사용 가능한 단위로 분리 |
| JSX | JavaScript 안에서 HTML처럼 UI를 작성 |
| 가상 DOM | 변경된 부분만 실제 DOM에 반영 |
| Hooks | 함수형 컴포넌트에서 상태와 사이드이펙트 관리 |
| Context | 전역 상태를 props 없이 공유 |
| 단방향 데이터 흐름 | 부모 → 자식 방향으로만 데이터 전달 |

> **정리:** 리액트는 컴포넌트 기반의 UI 라이브러리로, 가상 DOM과 단방향 데이터 흐름을 통해 예측 가능하고 효율적인 UI 개발을 가능하게 한다.

## 2. JSX

### JSX란?

**JavaScript XML**의 약자로, JavaScript 안에서 HTML과 유사한 문법으로 UI를 작성할 수 있게 해주는 문법 확장이다. React.createElement() 호출로 변환된다.

```jsx
// JSX
const element = <h1 className="title">안녕하세요</h1>;

// 변환 후 (Babel이 컴파일)
const element = React.createElement("h1", { className: "title" }, "안녕하세요");
```

### 브라우저는 JSX를 실행할 수 없는 이유

브라우저의 JavaScript 엔진은 표준 ECMAScript만 해석한다. JSX는 표준 JavaScript 문법이 아니므로 **Babel 같은 트랜스파일러가 표준 JavaScript로 변환**한 뒤에야 브라우저가 실행할 수 있다.

```
JSX → Babel 트랜스파일 → React.createElement() → 브라우저 실행
```

### JSX를 사용할 때의 이점

- **가독성** — UI 구조를 HTML처럼 직관적으로 표현할 수 있다
- **표현식 삽입** — `{}` 안에 JavaScript 표현식을 자유롭게 사용할 수 있다
- **컴파일 타임 오류 감지** — 문법 오류를 런타임 이전에 발견할 수 있다
- **IDE 지원** — 자동완성, 문법 강조 등의 도구 지원이 풍부하다

```jsx
const name = "홍길동";
const element = (
  <div className="card">
    <h1>{name}</h1>                          {/* 변수 삽입 */}
    <p>{2 + 3}</p>                           {/* 표현식 */}
    <p>{isLoggedIn ? "로그인" : "비로그인"}</p> {/* 삼항 연산자 */}
  </div>
);
```

> **정리:** JSX는 JavaScript 안에서 HTML처럼 UI를 작성하는 문법 확장이다. 브라우저는 JSX를 직접 이해하지 못하므로 Babel이 React.createElement()로 변환한다.

## 3. 컴포넌트

### 컴포넌트란?

**UI를 구성하는 독립적이고 재사용 가능한 단위**다. props를 입력받아 JSX를 반환하는 함수(또는 클래스)다.

```jsx
// 버튼 컴포넌트 — 재사용 가능한 단위
function Button({ label, onClick }) {
  return <button onClick={onClick}>{label}</button>;
}

// 여러 곳에서 재사용
<Button label="저장" onClick={handleSave} />
<Button label="취소" onClick={handleCancel} />
```

### 컴포넌트를 생성하는 방법

**1. 함수형 컴포넌트 (현재 표준)**

```jsx
function Welcome({ name }) {
  return <h1>안녕하세요, {name}</h1>;
}

// 화살표 함수
const Welcome = ({ name }) => <h1>안녕하세요, {name}</h1>;
```

**2. 클래스형 컴포넌트 (레거시)**

```jsx
class Welcome extends React.Component {
  render() {
    return <h1>안녕하세요, {this.props.name}</h1>;
  }
}
```

React 16.8에서 Hooks가 도입된 이후 함수형 컴포넌트가 표준이다. 클래스형은 레거시 코드에서만 볼 수 있다.

### 요소와 컴포넌트의 차이

| 구분 | 요소 (Element) | 컴포넌트 (Component) |
|---|---|---|
| 정의 | UI의 최소 단위, React.createElement() 결과 | 요소를 반환하는 함수 또는 클래스 |
| 형태 | 일반 객체 (plain object) | 함수 또는 클래스 |
| 불변성 | 생성 후 변경 불가 | 로직과 상태를 가짐 |

```jsx
// 요소 — React.createElement()의 결과물, 불변 객체
const element = <h1>안녕</h1>;

// 컴포넌트 — 요소를 반환하는 함수
function Greeting() {
  return <h1>안녕</h1>; // 요소를 반환
}
```

### 순수 컴포넌트란?

**동일한 props에 항상 동일한 JSX를 반환하는 컴포넌트**다. 사이드이펙트가 없고 외부 상태에 의존하지 않는다.

```jsx
// ✅ 순수 컴포넌트 — 같은 props면 항상 같은 결과
function UserCard({ name, age }) {
  return <div>{name} ({age}세)</div>;
}

// ❌ 순수하지 않은 컴포넌트 — 외부 상태에 의존
let count = 0;
function Counter() {
  count++; // 외부 변수 변경 — 렌더링마다 다른 결과
  return <div>{count}</div>;
}
```

React는 `React.memo()`로 순수 컴포넌트의 불필요한 리렌더링을 방지한다.

```jsx
const UserCard = React.memo(function UserCard({ name, age }) {
  return <div>{name} ({age}세)</div>;
});
// props가 변경되지 않으면 리렌더링 건너뜀
```

### 고차 컴포넌트(HOC)란?

**컴포넌트를 인자로 받아 새로운 컴포넌트를 반환하는 함수**다. 공통 로직을 여러 컴포넌트에 재사용할 때 사용한다.

```jsx
// 로딩 상태를 공통으로 처리하는 HOC
function withLoading(WrappedComponent) {
  return function WithLoading({ isLoading, ...props }) {
    if (isLoading) return <div>로딩 중...</div>;
    return <WrappedComponent {...props} />;
  };
}

const UserListWithLoading = withLoading(UserList);
const ProductListWithLoading = withLoading(ProductList);

// 사용
<UserListWithLoading isLoading={isLoading} users={users} />
```

React Hooks 도입 이후 HOC보다 커스텀 훅으로 로직을 공유하는 방식이 선호된다.

### 프래그먼트란?

컴포넌트는 반드시 하나의 루트 요소를 반환해야 한다. 불필요한 DOM 요소 없이 여러 요소를 반환할 때 **프래그먼트**를 사용한다.

```jsx
// ❌ 불필요한 div 추가
function List() {
  return (
    <div>
      <li>항목 1</li>
      <li>항목 2</li>
    </div>
  );
}

// ✅ 프래그먼트 — DOM에 추가 요소 없음
function List() {
  return (
    <>
      <li>항목 1</li>
      <li>항목 2</li>
    </>
  );
}

// key가 필요할 때는 명시적 문법 사용
function List({ items }) {
  return items.map(item => (
    <React.Fragment key={item.id}>
      <dt>{item.term}</dt>
      <dd>{item.description}</dd>
    </React.Fragment>
  ));
}
```

> **정리:** 컴포넌트는 UI를 구성하는 재사용 가능한 단위다. 함수형이 현재 표준이며, 순수 컴포넌트는 동일한 props에 동일한 결과를 보장한다. 고차 컴포넌트는 공통 로직을 재사용하는 패턴이고, 프래그먼트는 불필요한 DOM 요소 없이 여러 요소를 반환할 때 사용한다.

## 4. Props와 State

### Props란?

**부모 컴포넌트에서 자식 컴포넌트로 전달하는 데이터**다. 읽기 전용이며 자식에서 변경할 수 없다.

```jsx
// 부모
function Parent() {
  return <Child name="홍길동" age={25} />;
}

// 자식 — props를 받아서 사용
function Child({ name, age }) {
  return <p>{name} ({age}세)</p>;
  // ❌ props.name = "다른이름" — 변경 불가
}
```

### State란?

**컴포넌트 내부에서 관리하는 동적 데이터**다. 상태가 변경되면 컴포넌트가 리렌더링된다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>{count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}
```

### Props와 State의 차이

| 구분 | Props | State |
|---|---|---|
| 출처 | 부모 컴포넌트 | 컴포넌트 내부 |
| 변경 주체 | 부모만 변경 가능 | 컴포넌트 자신이 변경 |
| 불변성 | 읽기 전용 | `setState`로 변경 |
| 목적 | 데이터 전달 | 동적 상태 관리 |

### 리액트는 어떻게 여러 state를 일괄 처리하는가?

React 18부터 **자동 일괄 처리(Automatic Batching)** 가 도입됐다. 이벤트 핸들러 내의 여러 `setState` 호출을 하나로 묶어 리렌더링을 한 번만 실행한다.

```jsx
function handleClick() {
  setCount(c => c + 1); // 리렌더링 ❌
  setFlag(f => !f);     // 리렌더링 ❌
  // 여기서 한 번만 리렌더링 ✅
}
```

React 17 이전에는 이벤트 핸들러 내부에서만 일괄 처리됐고, `setTimeout`이나 `fetch` 콜백 내부에서는 각각 리렌더링됐다. React 18부터는 어디서든 일괄 처리된다.

### 자동 일괄 처리를 방지하려면?

`flushSync`를 사용하면 즉시 DOM에 반영할 수 있다. 하지만 성능이 저하되므로 꼭 필요한 경우에만 사용한다.

```jsx
import { flushSync } from "react-dom";

function handleClick() {
  flushSync(() => {
    setCount(c => c + 1); // 즉시 DOM 업데이트
  });
  // 이 시점에 DOM이 이미 변경됨
  flushSync(() => {
    setFlag(f => !f); // 즉시 DOM 업데이트
  });
}
```

### state 내부의 객체를 업데이트하는 방법

state는 직접 변경하면 안 되고 **새 객체를 만들어서** 설정해야 한다.

```jsx
const [user, setUser] = useState({ name: "홍길동", age: 25 });

// ❌ 직접 변경 — 리렌더링 안 됨
user.name = "김철수";
setUser(user);

// ✅ 스프레드로 새 객체 생성
setUser({ ...user, name: "김철수" });
```

### 중첩된 state 객체를 업데이트하는 방법

```jsx
const [form, setForm] = useState({
  name: "홍길동",
  address: {
    city: "서울",
    district: "강남구"
  }
});

// ✅ 중첩 객체 업데이트 — 각 레벨을 스프레드
setForm({
  ...form,
  address: {
    ...form.address,
    district: "마포구"
  }
});
```

중첩이 깊어질수록 복잡해지므로 Immer 라이브러리를 사용하면 불변성을 자동으로 관리해준다.

```jsx
import { useImmer } from "use-immer";

const [form, updateForm] = useImmer({ address: { city: "서울" } });

// 직접 변경하는 것처럼 작성 가능
updateForm(draft => {
  draft.address.city = "부산";
});
```

### key prop이란?

리스트를 렌더링할 때 각 항목을 **고유하게 식별하기 위한 특수 prop**이다. React가 어떤 항목이 변경/추가/삭제됐는지 파악하는 데 사용한다.

```jsx
// ❌ key 없음 — 경고, 비효율적 업데이트
{items.map(item => <li>{item.name}</li>)}

// ❌ index를 key로 — 순서 변경 시 오동작
{items.map((item, i) => <li key={i}>{item.name}</li>)}

// ✅ 고유 ID를 key로
{items.map(item => <li key={item.id}>{item.name}</li>)}
```

index를 key로 쓰면 항목의 순서가 바뀌거나 중간에 삽입/삭제될 때 React가 잘못 매핑해 예상치 못한 동작이 발생한다.

> **정리:** props는 부모가 자식에게 전달하는 읽기 전용 데이터, state는 컴포넌트 내부의 동적 데이터다. React 18의 자동 일괄 처리로 여러 setState가 한 번의 리렌더링으로 처리된다. 객체 state는 반드시 새 객체를 만들어 업데이트해야 한다.

## 5. 이벤트 처리

### 합성 이벤트란?

React가 브라우저의 네이티브 이벤트를 **래핑한 크로스브라우저 이벤트 객체**다. 모든 브라우저에서 동일하게 동작하도록 표준화된 인터페이스를 제공한다.

```jsx
function handleClick(e) {
  // e는 SyntheticEvent — 브라우저와 무관하게 동일한 인터페이스
  console.log(e.type);    // "click"
  console.log(e.target);  // 클릭된 요소
  e.preventDefault();     // 기본 동작 취소
}
```

React 17부터 이벤트가 `document`가 아닌 **루트 DOM 컨테이너**에 위임된다. 이를 통해 여러 React 버전이 같은 페이지에서 공존할 수 있다.

### 리액트 이벤트 핸들러와 HTML 이벤트 핸들러의 차이

| 구분 | HTML | React |
|---|---|---|
| 이벤트명 | 소문자 `onclick` | camelCase `onClick` |
| 핸들러 형태 | 문자열 `"handleClick()"` | 함수 참조 `{handleClick}` |
| 기본 동작 취소 | `return false` 가능 | `e.preventDefault()` 필수 |
| 이벤트 객체 | 브라우저 네이티브 | 합성 이벤트 (SyntheticEvent) |

```html
<!-- HTML -->
<button onclick="handleClick()">클릭</button>
```

```jsx
// React
<button onClick={handleClick}>클릭</button>
```

### 클래스 컴포넌트에서 이벤트 핸들러 바인딩

클래스 메서드는 기본적으로 `this`가 바인딩되지 않아 이벤트 핸들러로 전달하면 `this`가 `undefined`가 된다.

```jsx
class Counter extends React.Component {
  constructor(props) {
    super(props);
    this.state = { count: 0 };
    // 방법 1: constructor에서 bind
    this.handleClick = this.handleClick.bind(this);
  }

  handleClick() {
    this.setState({ count: this.state.count + 1 });
  }

  render() {
    return <button onClick={this.handleClick}>{this.state.count}</button>;
  }
}
```

```jsx
class Counter extends React.Component {
  state = { count: 0 };

  // 방법 2: 클래스 필드 + 화살표 함수 (권장)
  handleClick = () => {
    this.setState({ count: this.state.count + 1 });
  };

  render() {
    return <button onClick={this.handleClick}>{this.state.count}</button>;
  }
}
```

> **정리:** 합성 이벤트는 브라우저 간 일관성을 보장하는 React의 이벤트 래퍼다. HTML과 달리 camelCase 이름과 함수 참조를 사용한다. 클래스 컴포넌트에서는 이벤트 핸들러에 this를 바인딩해야 한다.

## 6. 가상 DOM과 파이버

### 가상 DOM이란?

**실제 DOM의 가벼운 JavaScript 객체 복사본**이다. React는 UI 변경 사항을 가상 DOM에 먼저 적용한 뒤, 실제 DOM과 비교해 변경된 부분만 업데이트한다.

```
state 변경
  → 새 가상 DOM 생성
  → 이전 가상 DOM과 비교 (Diffing)
  → 변경된 부분만 실제 DOM에 적용 (Reconciliation)
```

### 가상 DOM이 작동하는 방식

```jsx
// 1. 초기 렌더링
<ul>
  <li>Apple</li>
  <li>Banana</li>
</ul>

// 2. 상태 변경 후 새 가상 DOM
<ul>
  <li>Apple</li>
  <li>Banana</li>
  <li>Cherry</li>  ← 추가됨
</ul>

// 3. Diffing — React가 차이를 감지
// 4. 실제 DOM에 <li>Cherry</li>만 추가
```

**Diffing 알고리즘 규칙:**
- 다른 타입의 요소는 이전 트리를 버리고 새로 구축
- `key` prop으로 리스트 항목을 효율적으로 식별

### 섀도 DOM이란?

**브라우저가 제공하는 캡슐화된 DOM 서브트리**로, React와 무관한 웹 표준 기술이다. 내부 스타일과 마크업이 외부와 격리되어 영향을 주고받지 않는다.

```js
const host = document.querySelector("#widget");
const shadow = host.attachShadow({ mode: "open" });
shadow.innerHTML = `
  <style> p { color: red; } </style>  /* 외부 CSS와 충돌 없음 */
  <p>섀도 DOM 내부</p>
`;
```

주로 웹 컴포넌트(Web Components)에서 사용된다.

### 실제 DOM, 가상 DOM, 섀도 DOM 비교

| 구분 | 실제 DOM | 가상 DOM | 섀도 DOM |
|---|---|---|---|
| 주체 | 브라우저 | React | 브라우저 |
| 목적 | 실제 화면 구성 | 변경 감지 후 최소 업데이트 | 스타일/마크업 캡슐화 |
| 성능 | 직접 조작 시 느림 | 변경사항만 실제 DOM에 반영 | — |
| 사용 | 항상 존재 | React 내부에서 사용 | 웹 컴포넌트 |

### 리액트 파이버란?

React 16에서 도입된 **새로운 재조정(Reconciliation) 엔진**이다. 렌더링 작업을 작은 단위로 쪼개 우선순위를 부여하고 중단/재개할 수 있게 한다.

```
기존 (Stack Reconciler):
  렌더링 시작 → 끝날 때까지 중단 불가 → UI 블로킹 발생

파이버 (Fiber Reconciler):
  렌더링을 작은 단위(fiber)로 분할
  → 우선순위 높은 작업(사용자 입력) 먼저 처리
  → 긴 렌더링 중에도 UI가 반응
```

파이버를 기반으로 Concurrent Mode, Suspense, useTransition 같은 기능이 가능해졌다.

> **정리:** 가상 DOM은 변경된 부분만 실제 DOM에 반영하는 최적화 기법이다. 섀도 DOM은 스타일 캡슐화를 위한 웹 표준으로 React와 별개다. 리액트 파이버는 렌더링을 쪼개 우선순위를 처리하는 재조정 엔진이다.

## 7. Refs와 forwardRef

### refs란?

**DOM 요소나 컴포넌트 인스턴스에 직접 접근할 수 있는 참조**다. 렌더링과 무관하게 값을 유지하며, 변경해도 리렌더링이 발생하지 않는다.

```jsx
// useRef로 생성
const inputRef = useRef(null);

// JSX에 연결
<input ref={inputRef} />

// DOM에 직접 접근
inputRef.current.focus();
```

### refs의 주요 목적

- **DOM 직접 조작** — focus, scroll, animation 등 React로 제어하기 어려운 작업
- **서드파티 라이브러리 통합** — D3, 차트 라이브러리 등 DOM을 직접 다루는 라이브러리
- **이전 값 기억** — 리렌더링 없이 이전 state 값 보존

```jsx
function TextInput() {
  const inputRef = useRef(null);

  const handleFocus = () => {
    inputRef.current.focus(); // DOM 직접 접근
  };

  return (
    <>
      <input ref={inputRef} />
      <button onClick={handleFocus}>포커스</button>
    </>
  );
}
```

### state와 refs의 차이

| 구분 | state | refs |
|---|---|---|
| 변경 시 리렌더링 | ✅ 발생 | ❌ 발생 안 함 |
| 렌더링 중 읽기 | ✅ 가능 | ❌ 권장하지 않음 |
| 주요 용도 | UI에 반영될 동적 데이터 | DOM 접근, 리렌더링 없는 값 저장 |
| 초기화 | `useState(초기값)` | `useRef(초기값)` |

```jsx
// ✅ 카운터 — 화면에 표시되므로 state
const [count, setCount] = useState(0);

// ✅ 타이머 ID — 화면에 표시 안 됨, 리렌더링 불필요
const timerRef = useRef(null);
timerRef.current = setTimeout(() => {}, 1000);
```

### forwardRef란?

기본적으로 ref는 컴포넌트로 전달할 수 없다. `forwardRef`를 사용하면 **부모가 자식 컴포넌트 내부의 DOM 요소에 ref로 접근**할 수 있게 해준다.

```jsx
// forwardRef로 감싼 자식 컴포넌트
const Input = forwardRef(function Input({ placeholder }, ref) {
  return <input ref={ref} placeholder={placeholder} />;
});

// 부모에서 자식의 input DOM에 직접 접근
function Parent() {
  const inputRef = useRef(null);

  return (
    <>
      <Input ref={inputRef} placeholder="입력" />
      <button onClick={() => inputRef.current.focus()}>포커스</button>
    </>
  );
}
```

> **정리:** refs는 DOM 직접 접근이나 리렌더링 없이 값을 유지할 때 사용한다. state는 변경 시 리렌더링이 발생하지만 refs는 발생하지 않는다. forwardRef는 부모가 자식 내부 DOM에 ref로 접근하게 해준다.

## 8. 데이터 흐름과 컨텍스트

### 단방향 데이터 흐름이란?

데이터가 **부모 → 자식 방향으로만** 흐르는 구조다. 자식은 props를 통해 데이터를 받고 직접 변경할 수 없다.

```
App (state: user)
  ↓ props
Header (user.name 표시)
  ↓ props
Avatar (user.avatar 표시)
```

### 단방향 데이터 흐름의 이점

- **예측 가능성** — 데이터가 어디서 왔는지 추적하기 쉽다
- **디버깅 용이** — 상태 변화의 원인을 찾기 쉽다
- **명확한 책임** — 어떤 컴포넌트가 state를 관리하는지 명확하다

### 프롭 드릴링이란?

**중간 컴포넌트들이 props를 사용하지 않으면서 자식에게 전달만 하는 현상**이다.

```jsx
// ❌ 프롭 드릴링 — B, C는 user를 사용하지 않고 전달만 함
function A({ user }) {
  return <B user={user} />;
}
function B({ user }) {
  return <C user={user} />;
}
function C({ user }) {
  return <div>{user.name}</div>; // 실제 사용
}
```

### 컨텍스트란?

**컴포넌트 트리를 통해 전역적으로 데이터를 공유하는 방법**이다. props를 거치지 않고 어떤 컴포넌트에서든 데이터에 접근할 수 있다.

```jsx
// 1. 컨텍스트 생성
const UserContext = createContext(null);

// 2. Provider로 값 공급
function App() {
  const [user] = useState({ name: "홍길동" });
  return (
    <UserContext.Provider value={user}>
      <A />
    </UserContext.Provider>
  );
}

// 3. 어디서든 useContext로 접근 — B, C를 거치지 않음
function C() {
  const user = useContext(UserContext);
  return <div>{user.name}</div>;
}
```

### 컨텍스트의 목적

프롭 드릴링 문제를 해결하고, 테마, 인증 정보, 언어 설정처럼 **전역적으로 필요한 데이터를 공유**하는 데 사용한다.

단, 컨텍스트 값이 변경되면 해당 컨텍스트를 구독하는 **모든 컴포넌트가 리렌더링**되므로, 자주 바뀌는 데이터는 Zustand나 Redux 같은 상태관리 라이브러리를 사용하는 것이 낫다.

> **정리:** 단방향 데이터 흐름은 데이터를 예측 가능하게 만들어 디버깅을 쉽게 한다. 프롭 드릴링은 중간 컴포넌트가 사용하지 않는 props를 전달만 하는 문제로, 컨텍스트로 해결한다.

## 9. 렌더링 방식

### 서버 사이드 렌더링(SSR)이란?

**서버에서 HTML을 완성해 브라우저에 전달하는 방식**이다. 브라우저는 완성된 HTML을 받아 바로 표시하고, 이후 JavaScript가 로드되어 인터랙티브해진다(Hydration).

```
SSR 흐름:
  브라우저 요청
  → 서버에서 데이터 fetch + HTML 렌더링
  → 완성된 HTML 전달
  → 브라우저가 즉시 표시
  → JS 로드 후 Hydration (인터랙티브 활성화)
```

### CSR vs SSR

| 구분 | CSR (클라이언트 사이드) | SSR (서버 사이드) |
|---|---|---|
| 초기 HTML | 빈 HTML | 완성된 HTML |
| 초기 로딩 | 느림 (JS 로드 후 렌더링) | 빠름 (HTML 즉시 표시) |
| SEO | 불리 (크롤러가 빈 HTML 수집) | 유리 (완성된 HTML 제공) |
| 서버 부하 | 낮음 | 높음 |
| 이후 페이지 이동 | 빠름 | 페이지마다 서버 요청 |

```
CSR 흐름:
  브라우저 요청
  → 빈 HTML + JS 번들 전달
  → 브라우저에서 JS 실행 → 렌더링
  → 화면 표시 (초기 로딩 느림)
```

### 언제 SSR을 사용해야 하는가?

- **SEO가 중요한 경우** — 블로그, 뉴스, 쇼핑몰 상품 페이지
- **초기 로딩 속도가 중요한 경우** — LCP(Largest Contentful Paint) 최적화
- **소셜 미리보기가 필요한 경우** — OG 태그 렌더링

반면 대시보드, 어드민 페이지처럼 로그인 이후 접근하는 화면이나 SEO가 불필요한 경우는 CSR이 적합하다.

Next.js는 페이지별로 SSR/SSG/CSR을 선택할 수 있어 실무에서 가장 많이 사용된다.

> **정리:** SSR은 서버에서 완성된 HTML을 전달해 초기 로딩 속도와 SEO를 개선한다. CSR은 클라이언트에서 렌더링해 서버 부하가 낮고 페이지 이동이 빠르다. SEO와 초기 성능이 중요한 페이지에 SSR을 적용한다.
